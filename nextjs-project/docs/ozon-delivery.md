# Ozon Доставка для бизнеса

Подготовлена доставка заказов сайта в ПВЗ через актуальный [Ozon Delivery API](https://docs.ozon.ru/api/ozon-delivery/). Подключение относится к кабинету доставки для бизнеса. Ключи Seller API и старого Rocket API не подходят.

## Что реализовано

- Поиск активных ПВЗ в локальном кэше PostgreSQL, отдельно для каждой витрины и её метода доставки.
- Проверка доступности по телефону и расчёт доставки со страховкой на сервере.
- Вес и габариты из каталога, включая подарки; без заполненных параметров расчёт отклоняется. Все единицы складываются в одну коробку: максимальные длина/ширина и сумма высот. Упаковку и фактические габариты следует проверить на реальной сборке перед запуском.
- Расчёт действует 15 минут, привязан к телефону, витрине, ПВЗ, промокоду и составу корзины. Цена и адрес берутся из серверного расчёта. В транзакции заказа повторно проверяются расчёт и состав с подарками; один расчёт нельзя использовать для двух заказов.
- После оплаты создаётся одно отправление. Снимок запроса и UUID идемпотентности сохраняются вместе с заказом до обращения к Ozon. Повтор после сетевого сбоя использует те же данные.
- В раскрытой карточке заказа CRM: номер отправления, ошибка, повтор создания, обновление статуса, подтверждение готовности и этикетка PDF. Готовность подтверждает менеджер после проверки упаковки; автоматическое создание само по себе не означает готовность к передаче Ozon.
- Ошибки Ozon не откатывают оплату. Существующие варианты доставки доступны независимо от Ozon.

## Настройка и запуск

1. В кабинете Ozon Доставки создайте частное приложение и активный метод доставки с пунктами отгрузки и возврата. Для приложения нужны уровни `delivery-api.delivery`, `delivery-api.delivery-point`, `delivery-api.order`, `delivery-api.posting`.
2. Откройте **Админка → Настройки сайта → Ozon Доставка**. В одном блоке доступны **ВКЛ/ВЫКЛ**, **Client ID**, **Client Secret**, **ID метода доставки**, **срок передачи заказа** (1–168 часов, по умолчанию 24), **Проверить API Ozon** и **Обновить ПВЗ Ozon**. Выберите скоуп:
   - **Global** задаёт общие значения для двух витрин. Свои настройки витрины имеют приоритет, как у СДЭК.
   - **Inner Health** или **Sprint Power** — отдельные ключи, метод, срок и переключатель выбранной витрины.
   - В Global кнопка **Сохранить для обеих витрин** заменяет также индивидуальные настройки двух витрин. Это отдельное действие, обычное сохранение Global сохраняет их приоритет.

   Client ID и Client Secret хранятся в `SiteSetting` с существующим шифрованием настроек (в production требуется `SETTINGS_ENCRYPTION_KEY`). Сохранённый секрет не возвращается в форму: пустое поле сохраняет действующий секрет. При применении Global к обеим витринам переносится и сохранённый общий секрет. Настройки `ozon_*` читаются непосредственно из БД; переменные `OZON_CLIENT_ID`, `OZON_*_ENABLED` и другие прежние бизнес-настройки из окружения не используются.
3. Примените миграцию `20261025100000_add_ozon_delivery` штатным процессом проекта. Для Docker: `docker compose --profile ops run --rm migrator`. Для локального окружения: `npm run db:migrate` и `npm run db:generate`. Миграция создаёт кэш ПВЗ, расчёты и отправления; существующие заказы не изменяет.
4. Сохраните настройки в карточке Ozon. Проверьте API и обновите ПВЗ кнопками в этом же блоке. Проверка подключения и ручная синхронизация доступны и при выключенной доставке. Переведите переключатель в **ВКЛ** и сохраните. До появления свежих ПВЗ новый способ скрыт в корзине. Изменения применяются без перезапуска приложения. **ВЫКЛ** убирает Ozon из нового оформления; управление уже оплаченными отправлениями остаётся доступным с сохранёнными ключами.
5. Для ежедневного автоматического обновления настройте POST `/api/cron/ozon-points-sync` с заголовком `x-cron-token`, равным серверному `OZON_POINTS_SYNC_TOKEN`. Это инфраструктурный токен cron, ручная кнопка админки его не требует. Пример запуска из доверенного окружения, где токен уже задан:

   ```sh
   curl --fail --max-time 600 --request POST \
     --header "x-cron-token: ${OZON_POINTS_SYNC_TOKEN}" \
     "https://innerhealth.ru/api/cron/ozon-points-sync"
   ```

   Загрузка проходит все страницы, затем удаляет устаревшие ПВЗ. При ошибке старые записи не удаляются. Кэш старше 48 часов не используется. Не запускайте несколько синхронизаций одновременно.
6. Проверьте на согласованном тестовом заказе: ПВЗ и телефон, стоимость со страховкой, оплату, создание, повтор с тем же номером, подтверждение, обновление статуса и PDF. Внешние API и настоящая оплата при локальных автоматических тестах не вызываются.

## Диагностика подключения

Ozon может возвращать `expires_in` числовой строкой: она проверяется и преобразуется в число до расчёта срока кэша. Если в ответе есть `scope`, клиент проверяет наличие запрошенных прав Delivery API (либо уже выданного `delivery-api.all`). Токен с посторонними или неполными правами отклоняется до обращения к списку ПВЗ; админка предлагает проверить приложение и его ключи. Запрашиваемые разрешения при этом не расширяются.

Проверка API и обновление ПВЗ начинают с запроса списка пунктов. Для первой страницы клиент явно отправляет `pagination.cursor: null`; последующие страницы используют `next_cursor`. Кэш токена поддерживает абсолютный Unix timestamp в `expires_in` и относительный срок в секундах. Эти особенности реального API также описаны автором [ozon-delivery-business-python](https://github.com/databear/ozon-delivery-business-python#protocol-behavior); локальные регрессионные тесты проверяют оба формата срока и запрос первой страницы.

Админка различает этап получения OAuth-токена и вызова Delivery API. HTTP 401 указывает на отказ авторизации; HTTP 403 — на отсутствие доступа; HTTP 400 — на отклонённые параметры; HTTP 429 — на лимит запросов. Отдельные сообщения предусмотрены для сети/DNS, таймаута, неожиданных ответов, перенаправлений и явной блокировки с заголовком `antibot: 1`. Текст и тела ответов Ozon, ключи и данные получателя в диагностику не передаются. При сетевой ошибке нужно проверить доступ с сервера к `xapi.ozon.ru` и `api-delivery.ozon.ru`; при отказе доступа — права приложения и ограничения IP в кабинете Ozon.

## API проекта

| Маршрут | Назначение |
| --- | --- |
| `GET /api/ozon-delivery/status` | Готовность настройки и свежего кэша, без секретов |
| `GET /api/ozon-delivery/points?query=...` | Поиск города/адреса, до 30 результатов |
| `POST /api/ozon-delivery/quote` | `{items, phone, deliveryPointId, promoCodeId?}` → расчёт и `quoteToken` |
| `POST /api/orders` | `shipping.deliveryMethod=ozon_pvz`, `ozonDeliveryPointId`, `ozonQuoteToken` |
| `GET /api/admin/orders/:id/ozon-shipment` | Состояние отправления, только ADMIN |
| `POST /api/admin/orders/:id/ozon-shipment` | `{action: create|sync|approve|label}`, только ADMIN |
| `GET /api/admin/ozon-delivery/settings?brand=...` | Настройки выбранного скоупа и признак сохранённого секрета, только ADMIN |
| `PUT /api/admin/ozon-delivery/settings?brand=...` | `{settings, applyToBoth?}`; без `brand` — Global, только ADMIN |
| `POST /api/admin/ozon-delivery/check?brand=...` | Проверка сохранённых ключей без создания отправлений, только ADMIN |
| `POST /api/admin/ozon-delivery/points-sync?brand=...` | Обновление ПВЗ выбранной витрины; Global обрабатывает обе, только ADMIN |
| `POST /api/cron/ozon-points-sync` | Загрузка ПВЗ обеих настроенных витрин, только с cron-токеном |

## Границы первого этапа

Курьерская доставка, постаматы, возвраты и автоматическая отмена отправлений в этот этап не входят. Статус обновляется из CRM вручную. Покупатель отслеживает доставку в приложении Ozon. Подтверждение готовности может требовать положительного баланса в кабинете.

`cutoff_at` сохраняется в запросе как срок плановой передачи Ozon. После его истечения повтор создания сохраняет исходный запрос ради идемпотентности: если Ozon его отклоняет, менеджеру нужно проверить результат в кабинете и согласовать новый срок; менять сохранённый запрос и UUID без сверки нельзя.

Интеграция по умолчанию выключена. Для запуска заполните ключи рабочего кабинета через админку и проверьте реальные запросы к API в целевом окружении. Для самих настроек используется существующая таблица `SiteSetting`, дополнительная миграция не нужна.
