MAX SDK закреплён на 0.2.5. Для `https://platform-api2.max.ru` применяется отдельный
HTTP dispatcher с публичным Russian Trusted Root CA из официального источника Госуслуг.
Это требование [API MAX](https://dev.max.ru/docs-api/changelog-api).
Дополнительный CA действует только для этого origin; запросы к другим сервисам
сохраняют прежний dispatcher и доверенные сертификаты. Проверка TLS не отключается,
хранилища доверия ОС и контейнеров не изменяются. И web-приложение, и MAX runner
создают SDK-клиент через общий `createMaxBot`.
После этого исправления повторно прошли 786 тестов в 151 файле, обе проверки
TypeScript, сборка ботов, production standalone build и 8 браузерных сценариев.
Для MAX runner в Compose явно заданы DNS `1.1.1.1` и `8.8.8.8`: штатный резолвер
Docker на VPS периодически возвращал `EAI_AGAIN` для MAX API. После проверки с
этими резолверами оба runner работали без перезапусков. DNS хоста и остальных
сервисов не изменён.

Для разработки и проверки используется Node.js 22.18+ либо 24.11+ в соответствующих LTS-ветках.
Типы Node.js соответствуют Docker runtime 22.

## Совместимость инструментов

TypeScript 7 используется командой `tsc`. Пакет `typescript` указывает через npm alias на
`@typescript/typescript6`, поскольку ESLint, ts-node и другие потребители compiler API
продолжают использовать API TypeScript 6. Нативный CLI 7 установлен отдельно через alias
`@typescript/native`; его `tsc` и совместимый `tsc6` проверяются раздельно.
См. [объявление TypeScript 7](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/).

Перед основной проверкой типов `next typegen` генерирует типы маршрутов, в том числе на чистой установке.
Vitest использует `test.projects` для Node и jsdom; файловые директивы
`@vitest-environment jsdom` для отдельных `.test.ts` продолжают действовать.
См. [миграцию Vitest 5](https://vitest.dev/guide/migration/).

## Воспроизводимые проверки

Из корня репозитория:

```bash
npm ci
npm --prefix nextjs-project ci
npm run check
```

Генерация Prisma при установке требует `DATABASE_URL` в окружении приложения.
`check` последовательно выполняет lint, проверки TypeScript 7 и 6,
все Vitest-тесты, Next production build и сборку обоих ботов.
Для production build нужны обычные build-time переменные приложения.

Браузерные регрессии запускаются отдельной командой:

```bash
# В PATH должны быть сервер PostgreSQL, initdb и pg_ctl из одной установки.
npx playwright install chromium
npm run test:smoke
```

Если в PATH попали клиентские утилиты libpq, укажите полный каталог серверных бинарников:
`PG_BIN=/opt/homebrew/opt/postgresql@16/bin npm run test:smoke` (пример для Homebrew).

Команда создаёт собственный PostgreSQL-кластер во временной папке на свободном локальном
порту, применяет миграции и добавляет только тестовые товары двух брендов и пользователя.
Она собирает Next.js в production-режиме и запускает standalone-сервер на `127.0.0.1:3317`
со статикой и `public`, как в Docker-образе.
Уже работающий сервер не переиспользуется. Локальные `.env*` и секреты интеграций
не используются; внешние запросы браузера блокируются. При завершении сервер и временная база удаляются.

Проверяются desktop и mobile Chromium:

- каталог и карточка товара;
- добавление, количество, восстановление после перезагрузки и удаление товара из корзины;
- изоляция каталога Sprint Power;
- перенаправление гостя, вход пользователя и восстановление сессии;
- сообщение при неверном пароле и защита административных страниц/API.

Функциональность расчётов заказа, промокодов, доставки, обработчиков платежей и ботов
дополнительно проверяется существующими Vitest-тестами с подменой внешних сервисов.
Браузерный прогон не выполняет настоящие платежи и отправку уведомлений.
HTML-отчёт находится в `playwright-report/smoke`, trace и скриншоты ошибок — в `test-results`.

## Результат проверки 24 октября 2026

Проверено на Node.js 22.23.2, PostgreSQL 16.14 и Chromium из Playwright 1.64.1:

- 150 файлов Vitest, 778 тестов — успешно;
- 8 браузерных сценариев desktop/mobile — успешно, без пропусков;
- все миграции применены к чистой временной БД;
- production-сборка Next.js и запуск standalone — успешно;
- TypeScript 7 и совместимый TypeScript 6 — успешно;
- сборка Telegram- и MAX-ботов, загрузка compiler API через ts-node — успешно;
- lint — 0 ошибок, 1 существующее предупреждение о неиспользуемой `capabilities` в MAX webhook;
- версии прямых зависимостей bot/migrator runtime совпадают с lockfile приложения.

В этом прогоне не запускались Docker-сборка образов и реальные внешние API платежей,
доставки, почты и мессенджеров. Их обработчики проверены существующими тестами с моками.
