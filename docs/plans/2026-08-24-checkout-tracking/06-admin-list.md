# PR6 — Админка: список «Незавершённые оформления»

## Цель

Отдельный раздел в кастомной админке (ТЗ §13), визуально не смешанный с реальными
заказами, со списком/фильтрами/поиском (ТЗ §14, §18, §20).

Зависимости: PR1 (модели), PR2–PR5 (данные, которые показываем).

## Новые файлы

По прямому образцу существующего раздела заказов
(`nextjs-project/src/app/admin/orders/{layout.tsx,page.tsx}` +
`nextjs-project/src/app/api/admin/orders/route.ts`):

- `nextjs-project/src/app/admin/checkout-sessions/layout.tsx`
- `nextjs-project/src/app/admin/checkout-sessions/page.tsx` — список
- `nextjs-project/src/app/api/admin/checkout-sessions/route.ts` — `GET` со всеми
  фильтрами/пагинацией
- Пункт меню в существующей навигации админки (там, где сейчас ссылка на "Заказы") —
  **«Незавершённые оформления»**, отдельным пунктом, не подпунктом заказов, чтобы не
  создавать визуальную путаницу (ТЗ §13 явно требует "не смешивать").

## Таблица (ТЗ §14)

Колонки: Дата (created), Последняя активность, Клиент (fullName || "—"), Телефон,
Email, Корзина (`cartItemsCount` шт.), Сумма (`cartTotal`), Этап
(`currentStep`, человеко-читаемый лейбл — маппинг из PR7 переиспользуется здесь для
компактной версии причины), Причина (короткая человеко-читаемая строка), Статус
(бейдж: активен/брошен/ошибка оплаты/отменён/завершён — завершённые по умолчанию
скрыты, см. ниже), Заказ (ссылка на `/admin/orders/{orderId}` если есть, реиспользуя
существующую страницу заказа).

**По умолчанию `status = COMPLETED` не показывается в списке** (ТЗ, сценарий 6: "Он не
попадает по умолчанию в список незавершённых") — фильтр статуса по умолчанию =
`[ACTIVE, ABANDONED, PAYMENT_FAILED, PAYMENT_CANCELLED, EXPIRED]`, с возможностью явно
включить `COMPLETED` через фильтр "Статус" (полезно для аналитики полного пути, ТЗ §12).

## API `GET /api/admin/checkout-sessions`

Query-параметры (ТЗ §18):
- `dateFrom`, `dateTo` (по `createdAt`)
- `status` (multi)
- `step` (multi, по `currentStep`)
- `brand` — **обязателен** через `resolveAdminBrandFromRequest`, как во всех остальных
  admin-роутах; нельзя обойти передачей чужого `brand` в query, если текущий admin-юзер
  не имеет доступа к другой витрине (переиспользовать существующую проверку доступа
  admin-юзера к бренду, если она есть в `brand-request.ts`/auth-слое — уточнить при
  имплементации по факту текущей модели прав админов).
- `hasPhone`, `hasEmail`, `hasOrder`, `hasPayment` (boolean-флаги существования полей)
- `search` — по `phone`, `email`, `fullName`, `order.orderNumber`, `paymentId`
  (`OR`-условие, `contains`/`equals` в зависимости от типа поля; `orderNumber` —
  числовое точное совпадение, если строка парсится в число)
- `page`, `pageSize` (пагинация, как в остальных admin list API проекта)

Реализация queryset — через `checkout-session.service.listSessionsForAdmin(filters)`
(добавляется в PR2, но метод пуст/не используется до этого PR — здесь наполняется
реальной Prisma-логикой `where`/`orderBy`/`skip`/`take`).

## Storefront separation (ТЗ §19)

- `brand` — обязательный `where`-фильтр в каждом запросе к
  `listSessionsForAdmin`, без опции "показать все витрины" (если для заказов такой
  опции тоже нет — держим консистентность с существующим `admin/orders`; если есть —
  зеркалим то же поведение).
- Тест (см. PR9): запрос со `?brand=inner` не возвращает записи `brand=sprint-power`
  и наоборот.

## Что НЕ делать в этом PR

- Не переиспользовать страницу `/admin/orders` для показа незавершённых — отдельный
  раздел, отдельная таблица (ТЗ §13).
- Не тянуть полный `cartSnapshot`/timeline на страницу списка — только денормализованные
  поля для колонок; полные данные — в карточке (PR7), которая грузится по клику
  отдельным запросом.
- Не делать поиск полнотекстовым по `metadata` событий — поиск только по
  проиндексированным полям из ТЗ §20 (`phone`, `email`, `fullName`, orderNumber,
  paymentId).

## Проверка

- Список с товарами в брошенной корзине после выката PR1–PR5 показывает реальные
  записи, созданные ручным прогоном checkout без завершения оплаты.
- Фильтр по статусу/этапу/дате/бренду сужает список корректно.
- Поиск по номеру телефона находит сессию, введённую в PR3-тесте.
- `COMPLETED`-сессии не видны без явного фильтра.
