# PR9 — Сквозные тесты

## Цель

Добить тестовое покрытие из ТЗ §36, которое не укладывается точечно в PR1–PR8 (те PR
уже включают тесты своей функциональности — см. "Проверка" в каждом файле). Этот PR —
про сценарии, требующие данных/кода из нескольких предыдущих PR одновременно
(storefront isolation, полный funnel, идемпотентность callback'ов), плюс добивание
любых пробелов, обнаруженных по ходу PR1–PR8.

Зависимости: PR1–PR7 (весь функционал уже должен существовать).

## Backend-тесты (обязательный набор из ТЗ §36)

Расположение — рядом с существующими тестами проекта (найти актуальный test runner и
конвенцию именования по факту репозитория на момент имплементации; в проекте уже есть
`*.test.ts` рядом с исходниками, например `admin-stats-helpers.test.ts`).

- Создание checkout-session (гость и залогиненный).
- Сохранение guest-контакта, включая случай "чужой guestToken → сессия не найдена".
- Сохранение снимка корзины и его обновление при повторных вызовах.
- Переход между этапами (`currentStep`/`lastCompletedStep` обновляются корректно,
  нельзя "откатить" `lastCompletedStep` назад при повторном PATCH более раннего шага).
- Создание события (`CheckoutEvent` появляется с правильным `eventType`/`step`).
- Abandoned timeout — уже покрыт в PR5, здесь — интеграционный прогон через реальный
  HTTP-эндпоинт крона, не только сервисный слой.
- Возврат пользователя (`abandoned → active`, событие `CHECKOUT_REACTIVATED`, старое
  `CHECKOUT_ABANDONED` не удалено) — уже есть unit-тест в PR5, здесь — прогон полного
  пути "тик крона → abandoned → PATCH contact → active".
- `payment_failed` — полный путь от webhook до карточки (`getCheckoutReason`
  возвращает "Ошибка оплаты: …").
- `payment_succeeded` — полный путь, `CheckoutSession.status = COMPLETED`, связан с
  `orderId`.
- **Duplicate callback** — webhook ЮKassa вызывается дважды подряд с одним и тем же
  `succeeded`-статусом → `CheckoutEvent` с `PAYMENT_SUCCEEDED` создаётся один раз,
  `Order` не переходит в paid дважды (это уже гарантируется существующим
  `transitionOrderToPaid`, тест фиксирует, что checkout-tracking слой не ломает эту
  идемпотентность и сам ведёт себя так же).
- **Storefront isolation** — сессия с `brand='sprint-power'` не появляется в
  `listSessionsForAdmin({ brand: 'inner' })` и не открывается по прямому `GET
  /api/admin/checkout-sessions/[id]` с `?brand=inner` (404).
- **Permission isolation** — гость A не может PATCH-нуть сессию гостя B (чужой
  `guestToken`); залогиненный пользователь не может обратиться к чужой сессии по id
  без соответствующего cookie/сессии.
- **Отсутствие sensitive данных в metadata** — снапшот-тест (или grep-тест, см.
  PR8) по всем `CheckoutEvent.metadata`, созданным в тестовых сценариях с ошибкой
  оплаты и webhook callback.

## Admin/frontend-тесты (ТЗ §36)

- Отображение списка — рендерится таблица с ожидаемыми колонками на тестовых данных.
- Фильтры — каждый фильтр из PR6 сужает выдачу корректно (минимум: статус, этап,
  дата, storefront — как явно требует ТЗ §18).
- Карточка — все секции (клиент/корзина/checkout/платёж/заказ) рендерятся, включая
  случаи отсутствующих секций (нет платежа → секция скрыта или "—", не падает).
- Timeline — события отображаются в хронологическом порядке с человеко-читаемыми
  лейблами.
- Человеко-читаемая причина — `getCheckoutReason` протестирован на всех ветках из
  PR7 (по одному кейсу на каждый `currentStep`/статус/ошибку из словаря).
- Корректное отображение отсутствующих контактов — "не указано"/аналог, не пустая
  строка и не `undefined` в разметке.

## Что НЕ делать в этом PR

- Не дублировать unit-тесты, уже написанные внутри PR1–PR8 — этот PR добавляет то,
  чего там не было (в первую очередь — сквозные HTTP/интеграционные прогоны и
  storefront/permission isolation).
- Не тестировать сам ЮKassa/CDEK API боевыми вызовами — использовать существующие в
  проекте моки/фикстуры для внешних провайдеров (найти и переиспользовать, если уже
  есть моки для `yookassa.ts` в текущих тестах заказов; если нет — завести
  минимальные моки именно для checkout-tracking сценариев, не переписывая
  провайдерский клиент).

## Проверка

- Полный прогон тестового набора (`npm test` / актуальная команда проекта) зелёный.
- Ручной сквозной прогон всех 7 сценариев ТЗ §35 на staging/локально перед мёржем в
  прод-ветку — зафиксировать как последний шаг перед rollout (см. ТЗ §37, Этап 8).
